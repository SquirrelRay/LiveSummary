# 打包成 Windows .exe：調查、決定與步驟

第一階段（2026-10-14）的調查結果與使用者的決定。第二階段每一步開新視窗時先讀這份。
來源都是 2026-10-14 查的官方文件或 PyPI，實測數字都在這台電腦（RTX 4070 Laptop、Windows 11）量的。

## 使用者的決定（2026-10-14）

1. **程式碼公開，用 GPLv3 授權**（av 附的 x264/x265 是 GPL、載入在本程式程序裡，公開最單純）。
2. **資料位置**：設定類（config.json、介面設定、網址紀錄、版面配置、overlay 位置、詞庫、logs、翻譯錯誤紀錄）放 `%LOCALAPPDATA%\直播摘要`（**第4步改名為 `%LOCALAPPDATA%\LiveSummary`**，見「第4步結果」）；
   輸出（直播稿、摘要、聊天室、逐句翻譯、音訊）放「文件\直播摘要」（用 Windows Known Folder API 取得，OneDrive 重新導向也對）。~~沒打包時維持專案資料夾~~ → **2026-10-14 第2步改為：開發（直接跑 app.py）和打包版用同一套位置**，第一次啟動時從專案資料夾複製程式資料過去（舊輸出檔不搬）。
3. **第一版用壓縮檔**（免安裝資料夾），不做安裝程式。
4. **ffmpeg 改用 BtbN 的 LGPL shared 版**，固定某一版並備份對應原始碼。
5. **不附 cuDNN**（省 1.1 GB），第三階段驗證其他顯示卡。（授權收尾：ctranslate2 自帶的 cudnn64_9.dll 實測也用不到，一併不帶。）
6. **開發環境改用 Python 3.13**。

### 打包版不帶 av 與額外許可（2026-10-14，使用者決定）

- **決定：採用選項 3**（調查見下面「授權收尾結果」A）。理由：直播模式只傳 numpy 陣列，av 只是被 faster-whisper 匯入、從來不解碼；
  排除 GPL 函式庫（選項 1）不可行、PyPI 上沒有不含 GPL 的 av（選項 2），選項 3 實驗通過。不帶之後 x264／x265 不再隨附、也不在本程式程序裡，
  「NVIDIA 專有 DLL＋GPL 編碼器同程序」的疑慮消失，av.libs 25 個 DLL 的授權全文不用補，資料夾少約 65 MB。
- **做法**：
  - LiveSummary.spec 的 excludes 加 `av`；主程式的 Analysis 加執行期 hook `pyi_rth_av替身.py`：程式開始前，找不到真的 av 才在 sys.modules 放替身模組
    （faster-whisper 的 `import av` 才會成功）。替身任何屬性被用到就丟出 `沒有av錯誤`（RuntimeError）：「打包版沒有附 av（PyAV），不能讓 faster-whisper 直接讀音訊檔，
    只能傳 numpy 陣列…請把 logs\當機紀錄.txt 附上回報」，不會默默失敗。helper.exe 不載入 faster-whisper，不加 hook。
  - 開發環境（.venv）的 av 17.1.0、requirements、鎖定檔都不動；transcribe.py、scripts/vod_to_transcript.py 照常讀音訊檔。
  - 打包驗收（build_exe.av的檔案）：_internal 底下不能有 av、av.libs、av-*.dist-info，任何地方不能有 libx264／libx265（隨附 ffmpeg 的 avcodec 等不算），有就打包失敗。
  - 測試（tests/test_打包不帶av.py）：替身的錯誤訊息與 AttributeError 行為、找得到真的 av 時不放替身；
    另開 Python 模擬沒有 av → import faster_whisper 成功、decode_audio 讀檔案丟出中文錯誤（slow）；
    程式碼檢查：從 app.py、helper.py 沿 import 找到的專案模組裡，`.transcribe()`／`.detect_language()` 只准出現在 live_capture 的 載入模型／偵測語言／轉錄一段
    （以及只給開發工具的 transcribe.轉錄），不准用 decode_audio；傳檔案路徑的 transcribe.轉錄 只有 transcribe.main 呼叫，打包的模組不准用；
    再用只收 numpy 陣列的假模型實際跑 載入模型（試音）、轉錄一段、偵測語言。
- **GPLv3 第 7 條額外許可**（`LICENSE-ADDITIONAL-PERMISSION.txt`，打包時放在 exe 旁，列入必要檔案；LICENSE 的 GPLv3 全文不改）：
  - 用途：本程式和 NVIDIA、Intel 的專有函式庫在同一個程序裡連結——cuBLAS／cuBLASLt（隨附 DLL）、CUDA 執行期（ctranslate2.dll 靜態連結）、
    Intel OpenMP（libiomp5md.dll）、Intel oneMKL（ctranslate2.dll 靜態包含）。它們不是 GPL 相容授權、不能提供原始碼，GPL 的「系統函式庫例外」也不涵蓋；
    著作權人用額外許可明確允許這種結合並一起散布。
  - 條文照 FSF GPL FAQ「GPLIncompatibleLibs」的 GPLv3 範本（https://www.gnu.org/licenses/gpl-faq.html#GPLIncompatibleLibs），只填入函式庫與授權名稱；
    這些函式庫的原始碼無法提供，依 FAQ 說明拿掉大括號那一句。英文是正式條文，後面附中文說明。
  - 著作權人寫「RAYPORK」（2026-10-15 使用者指定，取代原本暫用的 git 作者名；version.著作權人 也是同一個名稱，exe 檔案內容的版權欄位用它）；範本的「or (at your option) any later version」保留（使用者確認），授權聲明維持獨立檔案的做法。
    FAQ 建議把許可聲明放進每個適用的檔案；目前只放一個獨立檔，並在 README、設定框「關於」、使用說明.txt、授權清單總表開頭指向它。
- **ctranslate2.dll 內含元件的授權聲明**（scripts/取得授權全文.py 新增 取ctranslate2內含()，→ `third_party_licenses\ctranslate2-內含-4.8.2\內含元件.txt`，附在 ctranslate2 那一項）：
  依 ctranslate2 v4.8.2 的 Windows 建置腳本（oneAPI Base Toolkit 2025.3.0、oneDNN 3.1.1 靜態、CUDA 12.8、`WITH_CUDNN=OFF`、`CUDA_DYNAMIC_LOADING=ON`、`BUILD_CLI=OFF`）
  與 CMakeLists／子模組：Intel oneMKL 2025.3.0（Intel Simplified Software License，授權檔取自 Intel 在 PyPI 的 mkl-include 2025.3.0）、oneDNN 3.1.1（LICENSE＋THIRD-PARTY-PROGRAMS）、
  spdlog、CCCL（thrust／cub／libcu++）、cpu_features、CUTLASS（各自子模組提交的授權檔）、BS_thread_pool.hpp、avx_mathfun.h、avx512_mathfun.h（檔頭的授權註解），
  以及 CUDA 執行期（cudart_static，CUDA EULA 附件 A）。ruy 只給 ARM、cxxopts 只給命令列工具、googletest 只給測試，沒編進去。
  （`WITH_CUDNN=OFF` 也證實了「授權收尾結果」B2 的實測：ctranslate2 根本沒用 cuDNN。）

### 授權收尾結果（2026-10-14）

**A. av 的 GPL 編碼器調查（只調查與實驗；.venv、鎖定檔都沒動；建議見最後，待使用者決定）**

     （FFmpeg 設定都有 --enable-libx264 --enable-libx265；14.4.0 沒有 Windows 版；13 以前沒有 3.13 的 wheel）。19.x 另外不相容 faster-whisper 1.2.1（open() 不收 metadata_errors），13.1～18.1 有這個參數。

  3. 打包時完全不帶 av，放一個替身模組讓 faster_whisper 能匯入 → **可行（實驗通過）**。
     - 做法（還沒做）：spec 的 excludes 加 `av`（av＋av.libs 約 67 MB 不帶）；加一個 PyInstaller 執行期 hook，在程式開始前把一個空的 `av` 模組放進 sys.modules，

     - 對開發工具：沒有影響（transcribe.py、VOD 腳本跑 .venv，有完整的 av；requirements、鎖定檔不變）。
     - 好處：x264／x265 不再隨附、也不在本程式程序裡 →「NVIDIA 專有 DLL＋GPL 編碼器同一個程序」的疑慮消失；av.libs 25 個 DLL 的授權全文不用補（下面 B5 也就不用做）。

  實測（Windows 11，在檔案總管雙擊 zip 內的 exe）：Windows 先跳系統警告「這個應用程式可能與此壓縮資料夾中的其他檔案有相依關係」（解壓縮全部／執行／取消）；
  選「執行」後，檔案總管只把那一個 exe 取出到 `%TEMP%\<GUID>_LiveSummary-v1.0.0.zip.xxx\LiveSummary\`，PyInstaller 開機程式在 Python 啟動**前**就找不到 `_internal\python313.dll`，
  跳英文的「Failed to load Python DLL」——所以「程式裡偵測旁邊沒有 _internal」**做不到**，Python 程式碼根本沒機會跑。
  - 試過的做法：用 Windows 內建的 .NET Framework 4 csc.exe 編一支約 6 KB 的 C# 小啟動器當 LiveSummary.exe，真正的主程式改成另一個檔名；檔案齊全才啟動主程式，缺檔跳中文提示。
    實機驗證過可行（zip 內雙擊 → 跳「請先把整個壓縮檔解壓縮，再執行 LiveSummary.exe」；正常解壓縮不誤擋）。
    （當時實測發現暫存資料夾是 `<GUID>_檔名.zip.xxx` 而不是猜的 `Temp1_…zip`，第一版判斷錯了才修正。）
  - **不採用的原因**：(1) 小型、沒有簽章、只負責啟動另一個 exe 的程式，很容易被防毒誤判（像木馬載入器），風險比使用者看到一句英文錯誤更大；
    (2) Windows 在使用者從壓縮檔內執行時本來就會先跳警告；(3) 程序名稱（工作管理員、防火牆）、工作列釘選、打包流程都變複雜。已完整移除。
  - 最後的做法：主程式維持 `LiveSummary.exe`（dist\LiveSummary 裡只有它和 helper.exe 兩個 exe），README 最前面用醒目方框寫「下載後請先把整個壓縮檔解壓縮，再執行 LiveSummary.exe」。發布頁、下載頁也要放同樣的話。
  - 其他評估過、不做：自己重編 PyInstaller 開機程式改訊息（要 C 編譯器與原始碼，每次升級都要重做）；把 `_internal` 改中文資料夾名（訊息仍是英文）；單檔 onefile（1.2 GB 每次啟動解壓縮，第2節已排除）。
- **版本號**：`version.py` 的 `版本 = "1.0.0"` 是唯一來源。讀取處：設定框最下面一行「直播摘要 v1.0.0」、當機紀錄標頭、LiveSummary.spec 產生 PyInstaller 版本資訊檔（LiveSummary.exe、helper.exe）、
  build_exe.py 的 zip 檔名 `LiveSummary-v1.0.0.zip`（舊的 LiveSummary*.zip 打包前一併清掉）、QApplication.setApplicationVersion。
  build_exe.py 驗收會用 pefile 讀兩個 exe 的 FileVersion／ProductVersion 必須等於 version.py；tests/test_版本號.py 檢查其他 .py／.spec 沒有寫死 1.0.0。
- **網址欄全形字**：`platforms.整理網址()`：全形 ASCII 區（U+FF01～FF5E）減 0xFEE0、全形空白→空白、「。」→「.」、去零寬空白與 BOM、去前後空白；中文、日文假名、半形片假名不動
  （不用 NFKC，會把半形片假名等也改掉）。套用在 `platforms.判斷()`、`names_page.頻道()`、啟動面板的「開始」（順便把網址框內的字改成半形）、主控台的「開始」。
- **圖示位置**：`assets\icon.ico`（`app_paths.圖示相對位置`）。有 → LiveSummary.spec 套用到 LiveSummary.exe、helper.exe，附進 `_internal\assets\icon.ico`，app.py 用 `app_paths.圖示檔()` 設視窗圖示；
  沒有 → 全部預設、打包不失敗。assets\README.txt 寫了規格。**圖示套到 PyInstaller exe 的路徑還沒用真的 .ico 完整打包過**（等 Ray 提供圖示後第一次打包時確認）。

## 1. Python 版本：3.13

- 3.10 已在 2026-10-01 停止支援；3.13 支援到 2029-10（devguide.python.org/versions）。
- 3.12 官方最後附安裝程式的是 3.12.10（2025-04），之後只出原始碼；3.13.16（2026-09-30）有官方 64 位元安裝程式（python.org/downloads/windows）。
- yt-dlp 2026.07.04 發布說明：建議版本提高到 3.11，3.10 的支援很快會拿掉。
- PyPI 逐一查過：requirements 裡所有套件（含相依）的釘選版本都有 cp313 或 abi3 的 Windows 安裝檔。av、onnxruntime 的最新版已不支援 3.10。
- 3.14 不選：numpy 2.2.6 沒有 cp314 安裝檔。
- **相依套件一定要鎖版本**：沒鎖時 3.13 環境裝到 av 19.0.1，faster-whisper 1.2.1 解碼音訊檔失敗
  （`TypeError: open() got an unexpected keyword argument 'metadata_errors'`）。直播轉錄傳 numpy 陣列不受影響，
  transcribe.py、scripts/vod_to_transcript.py 傳檔案路徑會壞。pytest 用假模型，抓不到這種問題 → 打包前一定要用真模型實測。

## 2. 打包工具：PyInstaller、資料夾形式（onedir）

- PyInstaller 6.22.3（2026-09-12）、pyinstaller-hooks-contrib 2026.8（2026-09-30）。
- 不用單一檔案：每次啟動要把約 1 GB 解壓到暫存資料夾，啟動慢；當掉時 `_MEI…` 不會刪（pyinstaller.org operating-mode）；也比較容易被防毒誤判。
- 預估大小（實測各元件）：cuBLAS 771 MB、PySide6 約 100～150 MB（只收用到的）、av 69 MB、ctranslate2 60 MB、numpy 55 MB、
  onnxruntime 48 MB、ffmpeg 約 70～110 MB、其他約 60 MB → 資料夾約 1.2～1.3 GB，壓縮檔約 0.8 GB。
- 轉錄模型不附（1.6 GB），維持第一次啟動時下載（first_run.py）。
- 打包時不用 UPX（`--noupx`），用 `--windowed`、`--icon`、`--version-file`。

## 3. streamlink 另開程序

- 打包後 `sys.executable` 是 exe 本身，`-m streamlink_cli`、`yt_audio.py` 都會失效（vod_to_transcript.py 是開發工具，不打包）。
- 做法：同一個打包資料夾多做一個命令列版 helper.exe（spec 裡兩個 EXE 共用一個 COLLECT／_internal），用參數切換 streamlink 模式與 yt_audio 模式。
  live_capture.py 由一個函式組指令：沒打包維持 `sys.executable -m streamlink_cli`，打包後改 `helper.exe --streamlink …`。
- 不讓主程式 exe 自己切換：主程式是無視窗模式，用管線傳二進位 stdout 是否可靠沒驗證；命令列版 exe 一定可以。
- 不改成程式內呼叫 streamlink：要重寫 streamlink → ffmpeg 的管線，停止時也不能直接 kill，改動大。
- 無視窗程式開 ffmpeg／helper 要加 `CREATE_NO_WINDOW`，不然會閃黑色命令列視窗（first_run.py 已有，live_capture.py 還沒有）。
- streamlink 外掛要 `collect_submodules('streamlink.plugins')`。

## 4. 顯示卡函式庫（實測）

- 轉錄時列出程序實際載入的 DLL：只有 `cublas64_12.dll`、`cublasLt64_12.dll`（771 MB）；nvidia-cudnn（1.1 GB）、nvrtc（179 MB）都沒載入。
  ctranslate2 自己附一個 cudnn64_9.dll 小檔（授權收尾實測：拿掉它轉錄結果一樣，打包不帶）。
- 只給 cuBLAS 也正常；兩種設定的差異和同一設定跑兩次的差異一樣大（26～32 行，顯示卡運算的正常浮動）。
- **只用 `os.add_dll_directory` 會失敗**（找不到 cublas64_12.dll），一定要同時加進 PATH（transcribe.找顯示卡函式庫 現在兩個都做）。
- 打包：cuBLAS 放 `_internal/nvidia/cublas/bin`，找顯示卡函式庫() 打包後改找 `sys._MEIPASS`。
- 授權：CUDA EULA 附件 A 列 cublas.dll、cublasLt.dll 為可散布（檔名可帶版本號）；只能給本程式用、不能移除版權聲明。
- 只在 RTX 4070 Laptop、large-v3-turbo、float16 測過。cuBLAS 12.9 需要的最低驅動版本還沒查（第二階段查 CUDA 相容性文件寫進 README）。

## 5. ffmpeg 與授權

- 現在用的 Gyan 9.0.2 full_build：gyan.dev 寫明所有版本都是 GPLv3；ffmpeg.exe 228 MB、編進幾十個函式庫，散布要附全部對應原始碼。
- 改用 BtbN `ffmpeg-n9.0-latest-win64-lgpl-shared-9.0`（73.7 MiB，2026-10-13 版）：固定某一天的版本、自己備份那一版原始碼，
  放在和下載檔同一處；附 LICENSE；關於畫面與下載頁寫明有用 FFmpeg（照 ffmpeg.org/legal 清單）。
- 我們是另開程序呼叫 ffmpeg，ffmpeg 的授權不影響本程式碼。
- av（faster-whisper 必裝）17.1.0、19.0.1 都附 libx264、libx265（GPL），載入在本程式程序裡 → 決定公開用 GPLv3。

  3. 關於畫面與下載頁寫明有使用 FFmpeg（ffmpeg.org/legal 的清單），不能暗示 FFmpeg 專案背書；
